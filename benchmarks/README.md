# Benchmarks

What `samemodel` measures on real engines, with everything needed to repeat it.
Every table below is generated by [`summarize.py`](summarize.py) from the files in
[`data/`](data/); no number is typed by hand.

## Setup

| | |
| --- | --- |
| Model | Qwen2.5-0.5B-Instruct. GGUF files `fp16`, `q8_0`, `q4_k_m` from [`Qwen/Qwen2.5-0.5B-Instruct-GGUF`](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF); MLX builds `bf16`, `8bit`, `4bit` from `mlx-community/Qwen2.5-0.5B-Instruct-*` |
| Prompts | the 60 built-in prompts, temperature 0, 128 new tokens, `top_logprobs` 10 |
| llama.cpp | build b12244 (commit `d5bbcd1f3`), official release binaries: `macos-arm64` and `ubuntu-x64` |
| MLX | mlx-lm 0.32.2, mlx 0.32.4, `mlx_lm.server` with its defaults |
| M4 | Apple M4, 10 cores, 16 GB, macOS 26.6.2. `llama-server -t 4 -c 16384 -np 4`; CPU runs add `--device none -ngl 0`, Metal runs `-ngl 99` |
| Xeon | Intel Xeon 6767P, Ubuntu 24.04, CPU only. `llama-server --device none -ngl 0 -c 16384 -np 4`, with `-t 4` for the unique-conversation selfchecks and `-t 2` for everything else. A shared machine with other load, which made the runs slow |
| samemodel | 0.1.0 |

Each configuration ran once, on a freshly started server.

A note on `seed`. `samemodel` sent `"seed": 1` with every request until we found
that `mlx_lm.server` does not batch requests that carry one (section 1, MLX). It
sends none now. All MLX data here was recorded again without a seed, except the
runs labelled "seed 1". The llama.cpp selfchecks with unique conversations and all
llama.cpp reference recordings still date from before that change; llama.cpp ignores
the seed in greedy decoding, and section 4 shows a recording repeated without it.
Add `EXTRA_ARGS="--seed 1"` to repeat those runs to the letter.

## Reproduce

```bash
# llama.cpp: download a release binary and the three GGUF files, then
bash benchmarks/llamacpp.sh <llama-server> <models dir> out/llamacpp-cpu
SERVER_FLAGS="-ngl 99" bash benchmarks/llamacpp.sh <llama-server> <models dir> out/llamacpp-gpu

# MLX: pip install mlx-lm, then
bash benchmarks/mlx.sh <python> out/mlx
EXTRA_ARGS="--seed 1" bash benchmarks/mlx.sh <python> out/mlx-seed

# tables
python benchmarks/summarize.py selfcheck "my CPU=out/llamacpp-cpu" --weights fp16 q8_0 q4_k_m
python benchmarks/summarize.py weights "my CPU=out/llamacpp-cpu" --steps fp16:q8_0 q8_0:q4_k_m
python benchmarks/summarize.py across "my CPU=out/llamacpp-cpu" "my GPU=out/llamacpp-gpu" --weights fp16 q8_0 q4_k_m
```

Each script starts a fresh server for every run and stops only the server it
started. On the M4 the three llama.cpp CPU configurations take about an hour in total.

## 1. One server, the same request under different conditions

`samemodel selfcheck` sends each prompt for the first time, then again on its own,
then again together with three unrelated requests. Every second prompt makes its
first request under load. That gives three comparisons:

- **cache reuse**: the first request, sent alone, against the repeat
- **first request under load**: the first request, sent in company, against the repeat
- **repeat under load**: the repeat against the third request, sent in company

"unique" conversations each start with a different system message, so a first
request has nothing to reuse. "shared" conversations have the same system message,
so a first request already reuses that cached prefix; one throwaway request puts it
in the cache before the measurement starts.

Each cell shows the verdict, how many outputs stayed identical, the argmax agreement
on positions with an identical context, and the median / 99th percentile drift of
the top-2 log-odds in nats. The last column is the share of prompt tokens the server
reported as served from its cache.

Reusing the prompt cache is exact for all three builds. Under load `mlx_lm.server`

section 2).

Identical in all four cases: a server that takes the same path gives the same
result, across restarts. For llama.cpp this also shows that the `seed` field makes
no difference to greedy decoding.

recordings made with a seed (served one at a time) against those made without
(served by the batch generator, in a batch of one):

| setup | comparison | identical outputs | argmax agreement | drift p50 | drift p99 | verdict |
| --- | --- | --- | --- | --- | --- | --- |

| MLX: seed 1 vs no seed | 4bit | 51/60 | 99.87% | 0.0078 | 0.0312 | noise |

it carries a seed, by about as much as batching changes it.

## What the numbers say

1. **A server that takes the same path twice gives the same answer twice.** Every
   Xeon row, Q8_0 on the M4 CPU, MLX cache reuse and the repeated recordings of
   section 4 are identical. The differences above come from a changed computation
   path, not from randomness.
2. **On the M4 CPU, Q4_K_M answers depend on the serving path.** Reusing the prompt
   cache or sharing the server with other requests moves the distribution by a
   median of 0.07 to 0.08 nat, the size of replacing fp16 weights with Q8_0 on that
   machine. Q8_0 on the same CPU is identical throughout, and fp16 shows only
   rounding noise.
3. **The same Q4_K_M file is exact on the Xeon** and several times quieter on Metal.
   The effect belongs to a combination of quantisation, backend and architecture,
   not to the quantisation format. For the M4 CPU, [`root-cause/`](root-cause/README.md)
   traces it to two things: a BLAS backend that takes over once a batch has 32 rows,
   and a pair of Q6_K kernels that round differently. With both removed the file is
   identical there too.
4. **Moving a quantised file to another backend or CPU architecture is itself a
   shift** of about a small quantisation step (0.06 to 0.09 nat), even between two
   setups that are each exact on their own. fp16 moves by rounding noise only.
5. **MLX reuses its prompt cache exactly, and batching moves its answers**: at the
   rounding level for the `8bit` and `4bit` builds, and by about as much as a small
   quantisation step for `bf16`.
6. **A request field can decide which path a request takes.** `mlx_lm.server` serves
   a request with a seed on its own and batches one without. The two paths give
   different answers even for a single request, and a measurement that sends a seed
   sees no batching at all. Our first version did exactly that.
7. **"How many answers changed" does not measure size.** It reads 75 to 90% for fp16
   to Q8_0 and 100% for Q8_0 to Q4_K_M, a step four to six times larger in drift.

## Caveats

- One small model, 60 prompts, one run per configuration. The ordering of effects is
  the finding; the decimals are not constants of nature.
- The cause is traced for one setup only, llama.cpp with Q4_K_M on the M4 CPU, in
  [`root-cause/`](root-cause/README.md). For llama.cpp's CPU kernels in general see
  [#25618](https://github.com/ggml-org/llama.cpp/issues/25618) and
  [#31504](https://github.com/ggml-org/llama.cpp/pull/31504).
- No CUDA backend, no vLLM, no SGLang yet.
- "Under load" depends on the server actually batching the simultaneous requests.
  `llama-server` ran with four slots; `mlx_lm.server` with its defaults.
- MLX reports log-probabilities in half precision, on a grid of 1/128 nat (`4bit`,
  `8bit`) or 1/16 nat (`bf16`). Drift below the grid reads as zero, so for `bf16` the
  argmax agreement is the number to read, and the verdict is based on it.
